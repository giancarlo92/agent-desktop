`secret` keeps passwords out of scripts, recordings and conversations. A person gives each one once, under a name; a script or an agent then writes it into a field by that name. No command ever returns a value.

The simplest way needs no setup: the first time a script or an agent runs `secret fill` with a name nothing is saved under, a small window asks the person for the password, saves it bound to that field's app and site, and the run goes on. Every later run fills it on its own. `secret set` saves one ahead of time instead.

```bash
agent-desktop secret set bank-login --app chrome.exe --site login.mybank.com   # asks for the value, hidden
agent-desktop secret list                                                     # names and bindings, no values
agent-desktop secret fill @s1abc:e7 bank-login                                # writes it into that field
agent-desktop secret delete bank-login
```

## Where they are kept

In the system's own secret store, encrypted with the user's account: Windows Credential Manager, the macOS Keychain, or the Secret Service on Linux (GNOME Keyring, KWallet), under the service `desktop-recorder-mcp`. Each entry holds the value and its binding, so a binding cannot be widened by editing a file. `~/.desktop-recorder-mcp/secrets.json` lists the names and bindings for `secret list`, never a value.

## set

`secret set NAME` asks for the value twice at a hidden prompt, so it needs a person at a terminal; the value is never an argument, which would show in process lists and shell histories. `--stdin` reads the first line of standard input instead, for a person who pipes it from their own password manager.

## fill

`secret fill REF NAME` writes the secret into the field `REF` names (from `snapshot` or `find`), the way `set-value` does, after checking that the field is a password field (unless `--any-field`), in the app and on the site the secret was saved for. It refuses with the reason otherwise. Its result says which secret was written and never contains the value; neither does an error. With the global `--headed`, it types the secret like a person, which fires the events a page listens for (a React or Vue form keeps its own copy of what was typed); without it, it sets the value directly, and the result's `method` is `set` with a note saying so. The result never says how long the secret is.

### The first time

When nothing is saved under `NAME` and the field is a password field, `fill` opens a window titled *agent-desktop: password needed*. It names the secret and where it will be used, and has one hidden box with **Save and continue** and **Cancel**. What the person types is saved in the secret store, bound to the field's app (`--app`) and, in a Chromium browser, to the page's host (`--site`), then written into the field; the result has `"saved_now": true`. The window gives the focus back to the window that had it, so a headed fill types into the right place. Cancel, closing the window, or five minutes without an answer stop the command with an error and save nothing. The value goes from that window to the secret store directly, so the agent or script that ran the command never sees it.

The window is the platform's own: a Win32 window on Windows, `osascript` on macOS, `zenity` or `kdialog` on Linux. Where none is available, save the secret first with `secret set`. No window is shown for a field that is not a password field.

## Through MCP

`agent-desktop mcp` offers `desktop_secret_list` and `desktop_secret_fill`. `secret set` and `secret delete` are never tools: an agent can use a secret a person saved, by name, but cannot save, read or delete one. A fill with a name nothing is saved under opens the first-time window for the person; the agent only learns whether it was given. A page that asks an agent to type a password somewhere else gets a refusal, because the secret is bound to its field, app and site.

## Limits

- Anyone who runs programs as the same user can read that user's secret store with the system's own tools; `secret` keeps values out of scripts, recordings, logs and agents' conversations, not away from the user's account.
- `secret` cannot run inside `batch`.
